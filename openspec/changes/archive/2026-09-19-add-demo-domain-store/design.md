## Context

Проект содержит стартовый React + TypeScript + Vite. Пользователь установил `mobx` (зависимость подтверждена в package.json). Создаём основу данных для одного демонстрационного заказа и одного пользователя. Модели и значения моков описаны в [domain-model.md](../../exploration/domain-model.md) и [demo-data.md](../../exploration/demo-data.md).

## Goals / Non-Goals

**Goals:** типизированные сущности, независимые воспроизводимые моки, один стор с данными и производными показателями.

**Non-Goals:** экран и подключение стора к React, установка UI kit или MobX, бизнес-команды создания ТМ и переноса, фильтры и выделение, сканирование и обработка КМ/КА, API, localStorage, обмен и печать. ТМ фиксирует выбранную пользователем упаковку без ограничений вместимости, веса или совместимости.

## Decisions

### Один небольшой предметный модуль

Предлагаемая структура: `src/domain/shipment/types.ts`, `demo-data.ts`, `shipment-store.ts`. Строгую FSD и слои repositories/services не вводим: сейчас есть один экран и локальные данные. Общий тип `ShipmentData` объединяет order и массивы products, containers, sourceLines, transportPlaces, allocationLines, markingCodes, aggregationCodes.

Все восемь сущностей и поля берём из описания моделей. Идентификаторы и штрихкоды — строки, количества и измерения — числа. `controlStatus` ограничен значением `checked`; отображаемую русскую подпись определит UI. Не создаём классы для отдельных записей, декораторы, схемы runtime-валидации и контракт REST.

### Фабрика данных и экземпляры стора

`createDemoData()` возвращает новый набор объектов и массивов при каждом вызове, включая массивы КМ внутри КА. `ShipmentStore` принимает набор данных в конструкторе, по умолчанию получает свежий набор из фабрики; создаёт собственную копию перед наблюдением. Передача данных нужна для небольших проверочных сценариев и не является API загрузки с сервера. Экспортируется класс, без глобального singleton и React provider на этом этапе.

Вместо общего изменяемого объекта это обеспечивает независимость экземпляров и исключает случайную порчу исходных моков. Создание нового стора возвращает исходное демо; публичная команда сброса пока не нужна.

### Реактивные данные и производные показатели

Используем поддерживаемый установленной версией MobX способ сделать данные observable и getters computed, без изменения глобальной конфигурации MobX. При реализации следует проверить доступный API установленного пакета.

Минимальная поверхность чтения:

- `data`: набор сущностей одного заказа;
- `orderTotals`: containers, sku, units, boxes, weightKg, volumeM3 по исходным строкам;
- `remainingLines`: исходные строки с вычисленным remainingQuantity, включая нулевые остатки;
- `remainingTotals`: те же показатели по положительным остаткам;
- `distributedUnits` и `distributionProgress`.

Количество источника не уменьшается: остаток вычисляется через allocationLines. Это сохраняет происхождение и исходные итоги. Хранение отдельного mutable remainingQuantity отвергнуто, чтобы не синхронизировать два значения.

SKU считаются уникально; число оставшихся контейнеров — по положительным остаткам. Короба, вес и объём считаются по характеристикам товара без предварительного округления. Прогресс измеряется по штукам; при пустом наборе строк равен 0, без NaN. Типы ТМ и распределения уже присутствуют, но бизнес-команды их изменения появятся позже.

### КМ/КА пока описывают только исходное состояние

КМ ссылается на sourceLineId; КА содержит markingCodeIds. Состав агрегата определяет количество единиц, вложенности нет. На этом этапе не добавляем сведения о назначении КМ в ТМ, сканирование и автоматический перенос кодов. Целостность исходного набора сверяется с описанием моков при реализации; пользовательский валидатор и ошибки UI не нужны.

### Проверка без тестовой инфраструктуры

По решению пользователя автоматические тесты, тестовые файлы, runner и тестовые зависимости на этом этапе не добавляем. Проверка реализации ограничена сверкой моделей и моков с описанием, сборкой `pnpm build` и линтером `pnpm lint`. Сценарии спецификации описывают ожидаемое поведение и не являются требованием написать тесты.

## Risks / Trade-offs

- Условные коды не соответствуют реальным форматам → явно сохраняем префиксы DEMO и откладываем распознавание.
- Числа с плавающей точкой → округление веса, объёма, коробов и процентов оставить UI; учитывать возможную погрешность при сравнении значений.
- Стор рассчитан на корректные локальные данные → проверки входящих API-данных и недопустимых переносов появятся с соответствующими возможностями, не маскировать неверные остатки обрезанием до нуля.
- Структура будущего REST API неизвестна → нынешние модели не объявляются серверным контрактом.

## Migration Plan

Миграций данных и изменений развёртывания нет. Модуль пока не подключается к экрану; откат ограничен добавленными файлами предметного модуля.

## Open Questions

Блокирующих вопросов нет. UI, операции распределения и обработка маркировки будут отдельными change.
