## Context

Перенос контейнера уже создаёт `AllocationLine` для остатка выбранного контейнера, но требует существующего активного ТМ. Пользовательский сценарий должен разрешать первый перенос без предварительного ручного создания ТМ. Будущие команды переноса товара будут нуждаться в том же механизме подготовки назначения.

## Goals / Non-Goals

**Goals:**

- Автоматически подготовить единственное целевое ТМ непосредственно перед валидным переносом контейнера.
- Использовать уже активное ТМ без создания дополнительного.
- Сделать кнопку переноса доступной при выбранном непустом контейнере независимо от наличия ТМ.

**Non-Goals:**

- Не добавлять перенос товарных строк, фильтрацию, частичные операции или изменения возврата.
- Не менять ручное создание и выбор ТМ.

## Decisions

### Подготовка назначения внутри команды переноса

Команда переноса сначала проверяет выбранный контейнер и его положительный остаток. Только после успешных проверок она использует активное ТМ либо создаёт новое через существующую операцию создания ТМ. Так пустое ТМ не появится из-за невалидного ввода, а будущая товарная команда сможет переиспользовать этот шаг.

Альтернатива — создавать ТМ уже при выборе контейнера — отклонена: выбор не должен менять данные и может быть отменён пользователем.

### Доступность следует возможности выполнить команду

Проверка доступности переноса больше не требует `activeTransportPlaceId`; достаточно выбранного существующего контейнера с остатком. Наличие ТМ остаётся проверяемым после его автоматической подготовки.

## Risks / Trade-offs

- [Команда теперь меняет две части состояния] → Сначала выполняются все проверки источника, затем создание ТМ и распределение в рамках одной синхронной команды стора.
- [Будущие команды могут дублировать правило] → Выделить подготовку назначения как отдельный внутренний метод стора до добавления переноса товара.
