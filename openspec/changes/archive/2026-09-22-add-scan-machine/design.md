## Context

`BarcodeInput` принимает завершённый ввод, но пока только пишет технический
лог. Прототип уже имеет локальные данные контейнеров, товаров и ТМ, однако
сканерный сценарий и доменные операции находятся в одном будущем рефакторинге.
Этот change создаёт независимую машину и resolver до подключения data store.

## Goals / Non-Goals

**Goals:**

- Сделать `ScanMachine` реактивным владельцем шага, краткого контекста и
  feedback сканерного сценария.
- Разрешать mock-коды до передачи их машине и не передавать в неё сырой текст.
- Соединить `BarcodeInput → input adapter → resolver → ScanMachine`.
- Сделать `transferring-*` наблюдаемым и блокирующим ввод состоянием.

**Non-Goals:**

- Исполнять effects, менять `ShipmentStore` или переносить товар.
- Заменять текущий `ShipmentStore` на `ShipmentDataStore`.
- Реализовывать backend-resolver, КМ/КА, печать, 1С либо сохранение.

## Decisions

### Разделение raw input, resolution и сценария

`BarcodeInput` передаёт непустое значение входному адаптеру. Адаптер вызывает
resolver, который делает `trim().toUpperCase()` и возвращает типизированный
`ScanEvent`. Машина получает только такой event. Это не позволяет правилам
формата штрихкода проникать в transitions и оставляет backend-resolver заменой
реализации, а не переписыванием машины.

### Контекст машины — ссылки, не доменные данные

Машина хранит только discriminated refs: source-context (`none`, container ID
или product ID) и active transport-place ID. Полные контейнеры, товары, остатки
и результаты расчётов в ней не дублируются. Будущий data store станет владельцем
этих данных и будет синхронизироваться явными mouse events.

### Состояние операции отдельно от устойчивого контекста

Устойчивые шаги: `ready`, `container-selected`, `product-selected`,
`awaiting-quantity`. Переходы к переносу представлены `transferring-*` и
содержат effect с уникальным ID. При ошибке машина возвращается к последнему
устойчивому шагу, сохраняя его контекст и публикуя локализованную feedback на
основе error code.

В этом change effect намеренно не исполняется. Поэтому `transferring-*` может
оставаться активным: это верное наблюдаемое состояние ожидания будущего
оркестратора, а не имитация успешного переноса.

### Короткие mock-коды

Mock-коды строятся по явным префиксам: `C1` для контейнера, `P1` для товара,
`TM1` для ТМ и `CMD:QTY` для команды количества. Exact matching после
нормализации выбран вместо определения по длине: форматы не пересекаются и
легко читаются при ручной проверке.

### Явная синхронизация мыши

Мышиные действия будут вызывать методы машины `mouseContainerSelected`,
`mouseProductSelected`, `mouseTransportPlaceSelected` и `mouseFilterCleared`.
Машина не использует MobX reaction на data store, чтобы не возникла скрытая
двусторонняя связь.

## Risks / Trade-offs

- [Transfer effect остаётся незавершённым] → Это ограничение явно отражено в
  UI «Обработка…»; следующий change подключит executor.
- [Контекст машины временно расходится с текущим store] → Мышиные события
  добавляются как явный контракт; синхронизацию effects реализует следующий
  change.
- [Mock-коды отличаются от реального формата] → Resolver изолирован и будет
  заменён без изменения event contract.

## Migration Plan

1. Добавить машину, resolver, adapter и mock-коды.
2. Подключить `BarcodeInput` к adapter-у и показать состояние машины.
3. В следующем change заменить технический input adapter на
   `ScannerWorkflowOrchestrator`, исполняющий effects через data store.

## Open Questions

- Полный список командных штрихкодов кроме `CMD:QTY` остаётся следующим change.
- Реальные префиксы и правила коллизий будут определены вместе с backend/WMS.
