## Why

Текущий `ShipmentStore` одновременно владеет данными заказа, производными
проекциями, фильтрами, UI-выбором и командами, поэтому его нельзя безопасно
использовать как независимую доменную основу для будущего scanner workflow.
Нужен отдельный data store с явным snapshot-contract и ID-ориентированными
операциями до миграции интерфейса.

## What Changes

- Добавить независимый реактивный `ShipmentDataStore`, который принимает один
  snapshot заказа извне через `setSnapshot` и не зависит от React,
  `ScanMachine`, `BarcodeInput` или `ScannerWorkflowOrchestrator`.
- Сделать store владельцем вычисляемых source/destination-проекций, остатков,
  итогов, активного ТМ и контекстного фильтра источника.
- Добавить атомарные ID-ориентированные команды создания и выбора ТМ,
  переноса и возврата данных; команды возвращают typed result со стабильным
  error code вместо зависимости от UI-selection.
- Зафиксировать детерминированный перенос следующей строки товара: первая
  строка исходного snapshot-а с положительным остатком.
- Добавить модульные тесты store и обновить exploration-документацию.

## Capabilities

### New Capabilities

- `shipment-data-store`: Независимое хранение snapshot-а формирования ТМ,
  проекции, фильтрация и typed доменные команды.

### Modified Capabilities

<!-- Нет: текущий интерфейс продолжает использовать ShipmentStore до отдельного change миграции. -->

## Impact

- Появится новый модуль data store и его тесты; текущий `ShipmentStore` и UI
  не изменяются и не получают новый store в этом change.
- Будущий `ScannerWorkflowOrchestrator` сможет вызывать публичные команды
  нового store, но не создаётся и не подключается сейчас.
- На этапе миграции рендера потребуется обновить существующие main specs,
  которые описывают `ShipmentStore`; это намеренно отложено, чтобы они пока
  соответствовали работающему UI.
