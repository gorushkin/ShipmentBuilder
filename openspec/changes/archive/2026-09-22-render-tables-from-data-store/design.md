## Context

`ShipmentPage` уже создаёт `ShipmentDataStore` и `ScannerWorkflowOrchestrator`, а оркестратор загружает в стор snapshot. Таблицы при этом всё ещё строят строки из старого `ShipmentStore` через функции форматирования. Требуется переключить только табличное чтение на новый источник, сохранив старый store для сводок и остальных ещё не мигрировавших частей страницы.

В UI есть два независимых режима источника (`containers` / `products`) и два режима назначения (`transport-places` / `transport-place-products`). Они нужны только панелям, поэтому остаются локальным UI-состоянием, не частью data store или orchestrator.

## Goals / Non-Goals

**Goals:**

- Предоставить из orchestrator read-only проекции строк обеих таблиц с параметром режима.
- Использовать один общий экземпляр orchestrator и `ShipmentDataStore` в странице и панелях, без передачи старого/new store через props.
- Отображать данные из нового snapshot store в четырёх режимах таблиц.
- Сохранить таблицы презентационными: клик по строке только отключён или пишет технический лог.

**Non-Goals:**

- Не подключать фильтр к кликам, сканированию или другим действиям.
- Не переносить и не возвращать данные в ответ на клики по строкам.
- Не мигрировать сводку заказа, остатки в нижней панели, диалоги и кнопки операций со старого `ShipmentStore`.
- Не переносить состояние режимов в orchestrator или `ShipmentDataStore`.

## Decisions

### Orchestrator exposes mode-specific table projections

Добавить две синхронные read-only функции, условно `getSourceRows(mode)` и `getDestinationRows(mode)`. Режим передаётся вызывающим UI; функции возвращают только DTO строк для выбранного режима. Они читают snapshot из принадлежащего orchestrator `ShipmentDataStore`, агрегируют метрики таблиц и не меняют состояние.

Левая проекция строится из положительных `remainingLines`: режим контейнеров агрегирует по контейнеру, режим товаров — по товару с количеством контейнеров, где остался товар. Правая проекция строится из списка транспортных мест и allocation lines; режим товаров показывает агрегированный состав только текущего активного ТМ. Короба, вес/объём и SKU рассчитываются по уже существующим правилам домена и текущему формату колонок.

Альтернатива — оставить форматирование строк в `pages/shipment/shared/format.ts` и дать UI прямой доступ к data store. Отклонена, поскольку договорённость этого изменения — получать данные через orchestrator, а не связывать компоненты с внутренней структурой стора.

### One shared runtime instance; no data-store props

Поскольку таблицы импортируют доступ к orchestrator, composition root должен экспортировать и повторно использовать один общий runtime экземпляр. `ShipmentPage` использует те же `ScanMachine`, `ShipmentDataStore` и `ScannerWorkflowOrchestrator`, что и панели; отдельные экземпляры в компонентах запрещены. Загрузка snapshot и `dispose()` остаются ответственностью жизненного цикла страницы.

Сами панели хранят локальный mode state и вызывают соответствующую проекцию в MobX `observer`-рендере. Presentational table components получают только типизированные строки, не получают `ShipmentStore`/`ShipmentDataStore`/orchestrator и не знают про фильтрацию.

Альтернатива — прокидывать store или orchestrator через props — отклонена в соответствии с выбранным пользователем способом доступа. Это не означает, что в props запрещены готовые DTO строк между панелью и нижележащей таблицей.

### Keep row interactions inert during this step

Режим рендера не меняет доменные данные. Обработчики выбора/фильтрации строк удаляются или заменяются на краткий `console.info` с типом сущности и ID. Фильтры, уже имеющиеся в `ShipmentDataStore`, этим изменением не активируются автоматически; новые table projections пока возвращают полный неотфильтрованный список.

### Keep the old store outside the table read path

`ShipmentStore` остаётся источником для заголовка заказа, сводок и существующих отложенных операций. Таблицы не читают его. Подключение mutation-кнопок к новому store и синхронизация временно разных моделей не входят в изменение.

## Risks / Trade-offs

- [Два стора могут временно показывать разные снимки] → Табличные компоненты читают только общий runtime нового стора; отдельно проверить используемый demo scenario loader. Миграция сводок и операций будет отдельным шагом.
- [Импортируемый singleton усложняет тесты и lifecycle] → Экспортировать один runtime composition module, держать запуск/остановку за страницей и покрыть повторный render/mount тестом; не запускать эффекты на уровне импорта.
- [Понятие «без props» можно чрезмерно распространить] → Не передавать store/orchestrator в props, но оставлять допустимыми пропсы готовых строк и чистые UI callbacks.
- [Таблица назначения товаров зависит от active ТМ, которое после загрузки snapshot может отсутствовать] → Режим остаётся переключаемым, projection возвращает пустой список, а таблица показывает согласованное пустое состояние; active ТМ не выбирается молча.

## Migration Plan

1. Выделить общий runtime composition и переключить страницу/панели на его единственный экземпляр.
2. Добавить типы row DTO и методы-проекции в orchestrator; заменить table row builders на эти методы.
3. Перенести режимы в локальное состояние соответствующих панелей и обезвредить обработчики строк.
4. Удалить старые table-only вычисления/зависимости от `ShipmentStore`, не удаляя форматирование, используемое остальными UI-частями.
5. Проверить четыре режима, реактивное обновление после загрузки snapshot, пустые данные, build, tests и lint.

Rollback — вернуть источники строк таблиц к `ShipmentStore` и удалить runtime projection integration; доменные данные не мигрируются и persistence не затрагивается.

## Open Questions

Открытых вопросов для этого этапа нет. Инертность кликов по строкам — временная; связывание их со scanner commands будет отдельным этапом.
