## Context

`BarcodeInputAdapter` already resolves raw input and directs unknown codes to
`ScannerWorkflowOrchestrator.barcodeUnknown()`. Оркестратор передаёт ошибку
машине, которая сохраняет её в persistent `feedback` для панели действий, но
одноразового уведомления нет. Документ требований задаёт для этой ситуации
текст «ШК не распознан». shadcn Toast предоставляет global `toast.add()` и
один компонент `Toaster` для отображения временных уведомлений.

## Goals / Non-Goals

**Goals:**

- Показать один toast типа `error` для каждого допустимого неизвестного скана.
- Сохранить тот же текст в feedback панели действий.
- Дать будущим прикладным сервисам единый интерфейс публикации alerts без
  импорта React или shadcn.

**Non-Goals:**

- Не показывать toast для других существующих ошибок, успехов или processing.
- Не менять barcode resolver, `ShipmentDataStore` или правила распределения.
- Не создавать очередь, историю уведомлений, действия в toast или повторные
  попытки.

## Decisions

### Issue создаёт машина, отображение запускает оркестратор

`ScanMachine.barcodeUnknown()` будет возвращать `ScanIssue | null`. В
допустимом состоянии она устанавливает feedback и возвращает
`barcode-unrecognized`; при transferring возвращает `null`. Оркестратор
немедленно направляет ненулевой issue в `AlertService`.

Это не даёт оркестратору отслеживать реактивное поле `feedback`, которое может
читаться многократно и породить дубли. Машина остаётся независимой от UI, а
оркестратор остаётся единственным отправителем alerts для workflow.

### AlertService отделён от shadcn

Контракт `AlertService.publish(alert)` принимает компактный объект с type и
текстом. Runtime создаёт shadcn-реализацию, вызывающую `toast.add`, и передаёт
её оркестратору. `Toaster` размещается один раз рядом с корнем ShipmentPage.

Альтернатива — прямой импорт `toast` в оркестратор — отклонена: она связывает
workflow с UI-библиотекой и не оставляет отдельной точки для будущих каналов
уведомлений. Альтернатива — хранить alerts в MobX-списке — отклонена для
первого шага: shadcn уже управляет жизненным циклом временного toast.

## Risks / Trade-offs

- [Toast скрывает постоянную ошибку после исчезновения] → feedback панели
  действий сохраняет тот же текст.
- [Повторная реакция покажет дубликат] → публикация происходит синхронно от
  одноразового `ScanIssue`, а не от наблюдения feedback.
- [Новый alert service начнут использовать для несогласованных строк] → в
  первом change доступен только один код и текст из документа требований.

## Migration Plan

Изменение локально для prototype: добавить service и UI renderer, затем
подключить его при создании orchestrator. Откат состоит в удалении renderer и
передаче no-op service; feedback машины продолжит работать.
