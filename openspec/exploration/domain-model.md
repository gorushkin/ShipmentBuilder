# Предметная модель демопрототипа ShipmentBuilder

Статус: описание для согласования, 18.09.2026. Код и схема REST API на этом этапе не создаются.

Источник: [описание процесса формирования транспортных мест](https://docs.google.com/document/d/1MFv8yPgM2O4uJkoNM9krBgWUKZr_21vJ/edit). Ограничения ниже отражают последующие договорённости по прототипу и сужают объём исходного документа.

## Границы первого этапа

- Цель — показать UI с минимальным набором операций на локальных моках.
- В один момент с заказом работает один человек.
- Состояние в дальнейшем будет храниться в памяти MobX. Перезагрузка возвращает исходные данные; сохранения в браузере нет.
- Бэкенд, REST API, реальный обмен с 1С и печать отсутствуют.
- Стек интерфейса: React, TypeScript, shadcn/ui на Base UI и Tailwind. Установку UI-инструментов пользователь выполняет самостоятельно.
- КМ/КА присутствуют в моделях и исходных данных. Их сканирование, проверки и обработка переноса будут отдельным этапом.
- Строгая FSD-структура не зафиксирована; организацию кода определим при реализации.

Названия полей ниже — рабочие обозначения для обсуждения, не контракт будущего API. Поля обязательны, кроме явно отмеченных необязательных.

## Сущности и связи

```text
Заказ
 ├── Контейнеры отбора
 │    └── Строки источника → Товар
 │         ├── КМ отдельных единиц
 │         └── КА → входящие КМ
 └── Транспортные места
      └── Строки распределения → Строка источника
```

### Товар (Product)

Справочное описание SKU. Количество зависит от контейнера и не хранится в карточке товара.

| Поле | Смысл |
| --- | --- |
| id | Внутренний идентификатор товара |
| code | Код товара для отображения |
| name | Наименование |
| barcode | Один демонстрационный штрихкод, строка |
| unitsPerBox | Количество штук в стандартном коробе, положительное целое |
| unitWeightKg | Вес одной штуки в кг |
| unitVolumeM3 | Объём одной штуки в м³ |
| isMarked | Требуется ли поштучная маркировка |

Упрощение: одна упаковочная кратность и один товарный штрихкод на SKU. Вес и объём служат для демонстрационных расчётов и не учитывают тару.

### Заказ (Order)

| Поле | Смысл |
| --- | --- |
| id | Внутренний идентификатор |
| number | Отображаемый номер заказа; в моках также код для выбора заказа |
| clientName | Название клиента без отдельного справочника клиентов |
| controlStatus | Для первого набора данных только «Проверен» |

Контейнеры и транспортные места связываются с заказом через orderId. Полный жизненный цикл заказа и признак готовности к отгрузке будут описаны позже, вместе с соответствующим UI. Проверку допуска к работе сейчас не моделируем.

### Контейнер отбора (PickingContainer)

| Поле | Смысл |
| --- | --- |
| id | Внутренний идентификатор |
| orderId | Заказ, которому принадлежит контейнер |
| barcode | Уникальный демонстрационный код контейнера, он же отображаемый номер |

Все контейнеры исходного заказа считаются проверенными. Отдельные статусы контейнеров пока не нужны.

### Строка источника (SourceLine)

Один товар в одном контейнере. Партии, серии и сроки годности не учитываются. Пара containerId + productId уникальна в рамках набора данных.

| Поле | Смысл |
| --- | --- |
| id | Собственный устойчивый идентификатор строки |
| containerId | Исходный контейнер |
| productId | Товар |
| quantity | Исходное количество штук до распределения, положительное целое |

Предлагаемая модель учёта: исходное количество сохраняется неизменным, остаток вычисляется из распределения. Это позволит показывать общий состав заказа и возвращать товар в исходный контейнер без отдельной истории операций.

### Транспортное место (TransportPlace)

Контейнер отгрузки, в который пользователь распределяет товар.

| Поле | Смысл |
| --- | --- |
| id | Внутренний идентификатор |
| orderId | Заказ |
| number | Отображаемый локальный номер, например «ТМ-001» |
| sequence | Порядок создания для сортировки |

Пустое ТМ допустимо. SSCC, тип тары, ограничения вместимости, PDF и статусы обмена пока не вводим. Локальный номер ТМ не является SSCC.

### Строка распределения (AllocationLine)

Связывает транспортное место с конкретной строкой источника. Даже одинаковый товар из разных контейнеров сохраняет происхождение; UI позже сможет группировать такие строки по товару.

| Поле | Смысл |
| --- | --- |
| id | Идентификатор строки распределения |
| transportPlaceId | Транспортное место назначения |
| sourceLineId | Строка источника |
| quantity | Распределённое количество штук, положительное целое |

Предлагаемое упрощение: одна строка на пару transportPlaceId + sourceLineId. Повторное добавление увеличивает её количество. Нулевые строки не нужны. Товар и исходный контейнер определяются через sourceLineId, без дублирования полей.

### Код маркировки (MarkingCode, КМ)

Идентифицирует одну единицу маркированного товара.

| Поле | Смысл |
| --- | --- |
| id | Внутренний идентификатор |
| value | Демонстрационное значение кода |
| sourceLineId | Исходная строка, определяющая товар и контейнер |

В исходных моках каждому экземпляру маркированного товара соответствует один КМ. Для немаркированного товара КМ отсутствуют. sourceLineId означает происхождение, а не текущее физическое расположение после переноса.

### Код агрегации (AggregationCode, КА)

Объединяет несколько КМ одной строки источника. В прототипе нет вложенных КА и агрегатов с разными товарами.

| Поле | Смысл |
| --- | --- |
| id | Внутренний идентификатор |
| value | Демонстрационное значение кода |
| markingCodeIds | Непустой список входящих КМ |

Количество товара в КА равно числу входящих КМ, а не одному скану. Один КМ принадлежит не более чем одному КА. Некоторые КМ могут не входить в КА. Товар и контейнер агрегата определяются по входящим КМ.

Привязка конкретных КМ к строкам распределения пока не определена: это часть будущей логики маркировки. Наличие исходных кодов не означает, что прототип уже умеет корректно распределять маркированный товар. До этого этапа такие операции не должны демонстрироваться как поддержанные; поведение элементов UI согласуем при работе над экраном.

## Количества и вычисляемые показатели

Базовая единица — целая штука. Дробные количества товара не поддерживаются; число коробов может быть дробным.

- Остаток строки = исходное количество − сумма её количеств во всех ТМ.
- Распределение не может превышать исходное количество; остатки неотрицательны.
- ШТ = сумма количества в выбранной области: заказе, контейнере, ТМ или остатках.
- SKU = число различных товаров с ненулевым количеством в соответствующей области.
- Короба = сумма quantity / unitsPerBox для каждого товара.
- Вес = сумма quantity × unitWeightKg; объём = сумма quantity × unitVolumeM3.
- Прогресс = распределённые штуки / исходные штуки заказа × 100%. Это предлагаемое для прототипа уточнение неопределённого в исходном описании «объёма заказа».
- Нераспределённые контейнеры = число контейнеров, в которых есть положительный остаток.

Агрегаты вычисляются, а не хранятся отдельными изменяемыми полями. Формат отображения и округление определим при разработке панелей; расчёты не должны суммировать уже округлённые значения.

## Что относится к состоянию интерфейса

Выбранный заказ, активное ТМ, выбранная строка, фильтр, режимы панелей и открытое модальное окно не являются предметными сущностями. Состав MobX-сторов обсудим на этапе реализации нужных частей экрана.
