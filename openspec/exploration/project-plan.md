# План прототипа Shipment Builder

## Цель

Собрать демонстрационный интерфейс формирования транспортных мест на локальных моках. Состояние живёт только в текущем сеансе; REST API, persistence и сканирование появятся позже.

## Техническая основа

- React, TypeScript и Vite;
- MobX и один `ShipmentStore`;
- Tailwind CSS и shadcn/ui на Base UI;
- CSS Grid для каркаса страницы;
- локальные данные без backend и browser storage.

## Следующий план: сканирование штрихкодов

Предыдущий порядок, где ближайшим шагом была самостоятельная логика КМ/КА,
больше не является актуальным планом. Сначала строится сквозной каркас
сканирования; КМ/КА будут добавляться в него отдельным последующим этапом.

### Этап 1 — ввод штрихкода

- [ ] Добавить независимую UI-фичу `BarcodeInput` перед информацией о текущем
  заказе и его характеристиках. Для поля использовать shadcn `Input`.
- [ ] В составе `BarcodeInput` добавить постоянно отрендеренную форму с input
  для штрихкода.
- [ ] В обычном режиме визуально скрывать input, не удаляя его из DOM и не
  лишая фокуса; сканер должен продолжать вводить в него данные.
- [ ] Добавить `BarcodeInputController`, владеющий input, submit формы,
  очисткой значения и восстановлением фокуса после обработки.
- [ ] Считать `Enter` единым терминатором сканирования и ручного ввода;
  сканеры должны быть настроены на отправку `Enter` в конце скана.
- [ ] Добавить кнопку и горячую клавишу `F2` для раскрытия поля ручного
  ввода; `Esc` возвращает его в скрытое представление.
- [ ] Не добавлять кнопку submit: и сканер, и редкий ручной ввод завершаются
  нативным submit формы по `Enter`.
- [ ] До подключения state machine submit выводит в консоль техническое
  сообщение `barcode completed` с нормализованным значением и ISO-временем.
- [ ] После действия мышью возвращать фокус на scanner input. Исключения:
  открытый модальный диалог или другое текстовое поле, в которое пользователь
  целенаправленно вводит значение.

### Этап 2 — машина состояний сканирования

- [ ] Добавить реактивную `ScanMachine` как свойство `ShipmentStore`.
- [ ] Передавать в неё только завершённый ввод: `barcodeCompleted(value)`.
- [ ] Описать состояния, переходы, подсказки и ошибки для контейнера,
  товара и транспортного места; обработку КМ/КА отложить.
- [ ] Хранить в машине сценарный контекст повторного сканирования
  (например, выбранный контейнер или товар), но не дублировать в ней
  доменные данные, фильтры и распределения.
- [ ] Машина не вызывает методы `ShipmentStore`; после каждого перехода она
  публикует декларативную одноразовую команду (`effect`).

### Этап 3 — новый оркестратор операций сканирования

- [ ] Добавить новый `ScannerWorkflowOrchestrator`; не переиспользовать
  прежний оркестратор, если он существует.
- [ ] Оркестратор наблюдает только за ID новой команды машины, исполняет её
  через публичные методы `ShipmentStore` и сообщает машине `succeeded` или
  `failed`.
- [ ] Каждая команда имеет уникальный ID и цикл жизни, исключающий повторное
  выполнение после реактивных обновлений.
- [ ] В первом наборе команд соединить сканы с существующими фильтрами,
  выбором активного ТМ и переносами контейнера/товара.

## Текущие ограничения прототипа

- Один пользователь работает с одним заказом.
- Ограничения вместимости транспортного места не моделируются.
- Изменения не сохраняются после перезагрузки.
- КМ и КА присутствуют в данных, но не участвуют в операциях.
- Сканирование пока не устанавливает контекст контейнера или товара: это
  временно делается действием мышью в строке. Ограничение снимается тремя
  этапами плана сканирования выше.
- Автоматические тесты пока не добавляются; проверка выполняется через lint, production build и браузерные сценарии.
