# Текущий scanner workflow

Реализован change `execute-scanner-transfers-and-returns`. Исторические этапы в
`project-plan.md` описывают предшествующие инкременты; текущая архитектура и
правила количественных операций описаны здесь.

## Сущности и связи

- `BarcodeInputController` управляет ссылкой на input и фокусом. Компонент
  постоянно рендерит форму, завершает ввод по Enter и уступает фокус диалогу.
- `BarcodeInputAdapter → BarcodeResolver` преобразуют строку в типизированное
  событие. Коды из таблиц сравниваются точно после trim и приведения к верхнему регистру; неоднозначное совпадение отклоняется.
- `ScanMachine` хранит шаг, source context, выбор товара/контейнера, pin исходной
  строки, товар назначения, активное ТМ и pending operation с ID. Она не читает
  данные заказа и не исполняет доменные операции.
- `ShipmentDataStore` получает snapshot извне, хранит исходные строки и
  распределения, вычисляет остатки, фильтры и итоги. Команды принимают явный
  scope и destination; проверка выполняется перед изменением allocations.
- `ScannerWorkflowOrchestrator` загружает моки, проверяет события выбора,
  синхронизирует filters и active ТМ, исполняет pending operation один раз и
  сообщает машине success/failure.

Таблицы, кнопки, summary и progress используют общий новый DataStore через
оркестратор. Старый ShipmentStore не участвует в странице. Режим левой таблицы
находится в оркестраторе, правой — локально в панели; режим не задаёт scope
доменных операций. При фильтре режим «Товары» показывает исходные строки с
контейнером, без фильтра — агрегированные товары.

## Команды прототипа

| Код | Действие |
|---|---|
| N00001, N00002… | Выбор контейнера; повторный скан переносит остаток |
| 10001, 10002… | Выбор товара; повторный скан переносит следующую строку |
| ТМ-001, ТМ-002… | Выбор ТМ и открытие его состава справа |
| CMD:CONTAINER | Весь выбранный контейнер |
| CMD:NEXT | Следующая положительная строка товара |
| CMD:LINE | Явно выбранная исходная строка |
| CMD:PRODUCT | Весь товар при product context |
| CMD:ALL | Все строки текущего фильтра |
| CMD:QTY | Открыть ввод количества переноса |
| CMD:RETURN-ALL | Вернуть всё из активного ТМ |
| CMD:RETURN | Вернуть выбранный справа товар или ожидать его скана |
| CMD:RETURN-QTY | Выбрать товар возврата, затем ввести количество |
| CMD:CANCEL | Отменить ожидание товара/количества |

Первый скан товара при фильтре контейнера переключает левый фильтр на товар
по всему заказу, очищает pin строки и ничего не переносит. Следующий скан того
же товара переносит следующую строку. Это согласованное уточнение исходного ТЗ.
Клик и явная команда переноса сохраняют работу с товаром внутри контейнера.
Вне фильтра контейнера совпадающий скан после выбора строки мышью переносит
именно её. Успех очищает pin, следующие сканы идут по порядку sourceLines
snapshot, пропуская нулевые остатки.

Обычный скан товара всегда адресует левую сторону, даже если товар уже находится
в ТМ. При нулевом остатке сохраняется фильтр товара и выводится «Весь товар уже
распределён». Только в явном ожидании товара для возврата скан адресует активное
ТМ. Скан ТМ открывает состав справа даже после сброса просмотра того же активного
места; левый фильтр сохраняется. Скан источника не меняет просмотр справа.

Для ручной проверки: F2 раскрывает ввод; `N00001` выбирает контейнер,
`10001` переключает на товар, повторный `10001` переносит строку; `ТМ-001`
(кириллические Т и М) открывает состав справа. В большом наборе принимаются
видимые `N-LARGE-001`, `SKU-0001`, `ТМ-001`. Внутренние C1/P1 остаются ID,
но больше не являются пользовательскими штрихкодами. КМ/КА не распознаются.


## Состояния и завершение

Устойчивые шаги: ready, container-selected, product-selected.
Дополнительные шаги: awaiting-return-product, awaiting-quantity, transferring.
Возврат также выполняется через transferring; направление хранится в operation.

В transferring input disabled и показано «Обработка…»; дополнительные действия
не исполняются. Оркестратор отправляет результат с ID, машина игнорирует
устаревшее completion. Синхронный prototype store не добавляет искусственной
задержки. После ошибки busy снимается, прежний контекст сохраняется.

После переноса source filter сохраняется даже при пустом результате. После
товара из контейнера машина снова ожидает следующий товар этого контейнера.
Возврат сохраняет source context и активное ТМ; выбор товара назначения
очищается после успеха. Переключение ТМ также очищает выбор товара назначения.

При валидном переносе без активного ТМ оркестратор создаёт и выбирает ТМ.
После загрузки snapshot первое существующее ТМ выбирается автоматически, если
выбор ещё отсутствует. Вручную созданное ТМ сразу становится активным.
Невалидная команда или отмена его не создаёт; возврат никогда не создаёт ТМ.
Неожиданная ошибка после создания оставляет пустое ТМ активным.

## Количество и отмена

Scope: выбранная строка → иначе товар выбранного контейнера → иначе все строки
товара. Количество проходит по строкам scope в стабильном порядке; из другой
строки при pin или из другого контейнера при container scope не добирается.
Возврат количества ограничен товаром активного ТМ.

Диалог хранит черновик локально, показывает актуальный максимум и принимает
целое число от 1 до него. Enter/кнопка отправляет quantity-submitted; перед
mutation остаток проверяется повторно. Невалидное число оставляет диалог открытым.
Escape, «Отмена» или ввод CMD:CANCEL + Enter отменяют ожидание. Фокус
возвращается в barcode-input. Отмена уже выполняемой операции не поддерживается.

SourceLine, КМ и КА не меняются. Backend, persistence и проверка маркировки
остаются будущими этапами.
